# LLM Obsidian v2.5.0

Version 2.5.0 lets the model propose a task-specific pipeline when the
code-owned selector proves that the 2.4 built-ins do not fit. The proposal is
bounded data, not executable code, and still runs through the single existing
harness lifecycle.

## Highlights

- Exact `PipelineSpec` JSON schema and strict parser with canonical definition
  hashing, primitive/capability resolution, context bounds, and conservative
  node/model/loop budgets.
- Deterministic baseline selection rejects custom definitions that merely
  restate `lifecycle/default`, `engineering/change`, or `engineering/fix`.
- The approval preview shows the baseline delta, inherited route, enforcement
  bindings, absolute worst case, loop stops, review mode, effects, and terminal
  outcomes. Validation persists a pending exact challenge; only the host-owned
  macOS decision dialog can produce the random one-shot launch token. No
  decision value is accepted through model-accessible argv or stdin.
- Custom pipelines compose registered model steps, optional verification, and
  the existing final review. Typed transitions may branch or loop backward only
  within code-owned traversal and model-call ceilings. `parallel`/`join` and
  arbitrary commands remain unavailable.
- Per-visit child operations and immutable receipts provide exact replay and
  resume from the first missing step without a second store, FSM, scheduler, or
  provider session.
- Registered extra checks are appended by code to the existing verification
  profile; the model names check IDs and never supplies commands.
- A code-only liveness ladder reconciles stable result-without-submit evidence,
  records suspected idle after ten minutes, permits one nudge and one
  operation-global identity-bound restart without replaying the original
  prompt, and then returns durable attention. Raw screens,
  prompts, specs, results, and decisions never enter telemetry.
- Durable review callbacks send one idempotent wake to their exact coordinator,
  so a completed reviewer does not leave the current-checkout gate sleeping.
- Custom start consumes its token while installing the immutable approved
  spec/plan/prompt/route/review snapshot; mutable source paths are not reread to
  construct a different frozen definition.
- Content-free promotion reporting identifies repeated successful custom
  definition fingerprints. Promotion remains a manual registry/TDD/review
  change.
- `features.custom_pipeline_authoring` is the rollback switch for new custom
  definitions. Built-ins and frozen active definitions do not depend on it.

## Security boundary

- Model output cannot select a more permissive baseline, provider, filesystem
  path, command, dependency, credential, permission, or side-effect class.
- Only code/sandbox-enforceable permission and effect bindings are declarable;
  policy-only cmux claims are rejected for custom specs.
- Context pointers must match the approved plan/context packet by exact hash and
  declared byte bound before launch.
- The authoring model cannot approve its own proposal, mutate a frozen run, or
  widen the global policy ceiling.
- Push, publish, deploy, destructive operations, dependency installation,
  worktree deletion, and scope expansion remain outside unattended authority.

See [the 2.5 boundary ADR](../decisions/v2.5-model-authored-pipeline-boundary.md)
for the complete trust and execution decision.

## Clean install

```bash
git clone --branch v2.5.0 https://github.com/zerg-su/llm-obsidian.git
cd llm-obsidian
bash bin/setup-clean-machine.sh

python3 scripts/codex-adapter.py --check
scripts/mcp-gateway/mcp-gateway.sh codex-sync --check
python3 scripts/harness-cli.py doctor
```

For Codex, install the local marketplace/plugin and then start a new thread:

```bash
codex plugin marketplace add "$(pwd)"
codex plugin add llm-obsidian@llm-obsidian-codex
```

## Upgrade from 2.4.1

Finish or cancel active task, review, research, and reap operations before
changing the checkout:

```bash
python3 scripts/upgrade-preflight.py --vault-root .
git pull --ff-only
python3 scripts/codex-adapter.py --apply
scripts/mcp-gateway/mcp-gateway.sh codex-sync --apply
python3 scripts/harness-cli.py doctor
```

The runtime does not translate active 2.4.1 state into a custom definition.

## Release gate

```bash
make test
make acceptance-check
python3 scripts/validate-vault.py --summary
python3 scripts/codex-adapter.py --check
scripts/mcp-gateway/mcp-gateway.sh codex-sync --check
git diff --check
```

The checked-in dogfood report must cover at least ten completed approved custom
runs after built-in-fit rejection across Claude/Codex routes, change/fix
semantics, a bounded loop, review verification, deliberate escalation,
result-without-submit, live idle, provider death, and exhausted recovery. It
must report no permission escape, duplicate accepted effect, unresolved
callback failure, or auto-close miss.

The completed evidence and the distinction between live-model runs and
deterministic production-controller fault injection are recorded in
[the v2.5 dogfood report](../acceptance/v2.5.0-dogfood.md).

## Rollback

For new work, set `features.custom_pipeline_authoring=false` in
`config/harness.toml`; built-ins remain available. Finish or park frozen custom
runs before reinstalling 2.4.1:

```bash
git switch --detach v2.4.1
python3 scripts/codex-adapter.py --apply
scripts/mcp-gateway/mcp-gateway.sh codex-sync --apply
python3 scripts/harness-cli.py doctor
```

## Maintainer release commands

Run only after final review and release checks are green:

```fish
set RELEASE_SHA (git rev-parse HEAD)
test (count (git status --porcelain)) -eq 0

git push origin main
set REMOTE_SHA (git ls-remote origin refs/heads/main | string match -r '^[0-9a-f]+')
test "$REMOTE_SHA" = "$RELEASE_SHA"

git tag -a v2.5.0 $RELEASE_SHA -m "LLM Obsidian v2.5.0"
git push origin v2.5.0
git ls-remote --exit-code origin refs/tags/v2.5.0

gh release create v2.5.0 \
  --repo zerg-su/llm-obsidian \
  --title "LLM Obsidian v2.5.0" \
  --verify-tag \
  --notes-file docs/releases/v2.5.0.md
```
