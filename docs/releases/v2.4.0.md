# LLM Obsidian v2.4.0

Version 2.4.0 adds compiled, state-free pipeline reconciliation without
replacing the restartable harness introduced in 2.3. The release deliberately
keeps one execution engine and one operation identity: dispatch, review,
research, reap, replay, repair, cmux lifecycle, and exact cleanup still run
through the proven harness kernel.

## Highlights

- Frozen code-owned descriptors for:
  - `lifecycle/default`: dispatch → review → reap-ready;
  - `engineering/change`: TDD slices → verify → review → reap-ready;
  - `engineering/fix`: reproduce → root cause → regression test → minimal fix
    → verify → review → reap-ready.
- Pure compilation validates exact primitive versions, schema chaining,
  session modes, installed skill semantics, and route capabilities.
- Canonical serialization produces a stable definition SHA-256.
- `dispatch-runner.py validate` now includes the lifecycle definition hash and
  a bounded summary in the existing read-only pre-approval response.
- The summary labels state-free harness execution plus sandbox- and
  code-policy-enforced bindings; rendering it creates no worktree, provider
  session, or external effect.
- A completed executor summary triggers the code-owned review facade. New
  callback evidence and resolution HEAD changes advance that same gate
  idempotently; unchanged state creates no repeated review effect.

## Net-value gate

The original 2.4 experiment also implemented a second controller, receipt
ledger, and shadow layer. The specification required a Fable gate before any
production switch:

- added non-test LOC at the gate: 1,364;
- honestly deletable existing orchestration: 100–400 LOC.

Because deletable LOC did not exceed added LOC, that second-engine composition
switch was cancelled. The controller, ledger, second operation identity, and
pseudo-shadow product module were removed. Detached budget/security claims and
unimplemented `human_gate`/`bounded_loop` primitives were also removed.

The user later restored the executable 2.4 goal and approved a smaller
architecture: the existing operation and review records remain the only
durable state while the compiler owns ordering. See the
[original composition ADR](../decisions/v2.4-pipeline-composition-boundary.md)
and its
[state-free successor](../decisions/v2.4-state-free-executable-lifecycle.md).

## What does not change

- No second workflow engine, scheduler, store, FSM, supervisor, operation
  identity, or CLI.
- No model-authored or user-authored pipeline DSL.
- No compatibility layer or runtime-state migration.
- Executor sessions receive the exact linked-worktree Git metadata and cmux
  socket grants already required by unattended dispatch. Review launch and
  callback driving move from model instructions into the harness.
- No change to research isolation, replay, cleanup, or cmux placement behavior.
- `reap` remains a coordinator-owned terminal transaction.

The separate 2.5 custom-pipeline plan does not begin until 2.4 has a real
dogfood window and passes its own release gate.

## Clean install

```bash
git clone --branch v2.4.0 https://github.com/zerg-su/llm-obsidian.git
cd llm-obsidian
bash bin/setup-clean-machine.sh

python3 scripts/codex-adapter.py --check
scripts/mcp-gateway/mcp-gateway.sh codex-sync --check
python3 scripts/harness-cli.py doctor
```

Install the local marketplace/plugin through the Claude Code plugin UI. For
Codex:

```bash
codex plugin marketplace add "$(pwd)"
codex plugin add llm-obsidian@llm-obsidian-codex
```

Start a new Claude/Codex thread after installation so the host loads the 2.4.0
skill registry and plugin metadata.

## Upgrade from 2.3.0

Finish or cancel active operations before changing the checkout. Then update
the plugin adapters and start a new agent thread:

```bash
git pull --ff-only
python3 scripts/codex-adapter.py --apply
scripts/mcp-gateway/mcp-gateway.sh codex-sync --apply
python3 scripts/harness-cli.py doctor
```

The durable operation schema is unchanged, but an in-flight operation must
finish under the checkout that started it.

## Verification

Model-free release checks:

```bash
make test
make acceptance-check
python3 scripts/validate-vault.py --summary
python3 scripts/codex-adapter.py --check
scripts/mcp-gateway/mcp-gateway.sh codex-sync --check
git diff --check
```

`make acceptance-live` remains the maintainer-only provider gate. It must
produce four schema-valid cells for the exact release SHA before publication.

## Rollback

Finish or cancel all active operations and use a fresh previous checkout:

```bash
git switch --detach v2.3.0
```

## Maintainer publication

Run only after a clean release commit, exact-SHA live acceptance, and final
review:

```bash
RELEASE_SHA="$(git rev-parse HEAD)"
test -z "$(git status --porcelain)"

git push origin main
test "$(git ls-remote origin refs/heads/main | awk '{print $1}')" = "$RELEASE_SHA"

git tag -a v2.4.0 "$RELEASE_SHA" -m "LLM Obsidian v2.4.0"
git push origin v2.4.0
git ls-remote --exit-code origin refs/tags/v2.4.0

gh release create v2.4.0 \
  --repo zerg-su/llm-obsidian \
  --verify-tag \
  --notes-file docs/releases/v2.4.0.md
```

The tag is authoritative; the release command intentionally omits `--target`.
