# LLM Obsidian v2.6.4

Version 2.6.4 is a harness-reliability patch release. It closes unattended
callback, continuation, decision-history, plan-review, reviewer-cleanup, and
Wiki-validation gaps found while dogfooding 2.6.3. It does not add a scheduler,
change PipelineSpec DSL, expand provider or permission policy, or increase any
review, verification, nudge, restart, or model-call budget.

## Unattended callback continuity

The harness now distinguishes model prose, transport acceptance, provider
generation acknowledgement, typed callback acceptance, and terminal cleanup.
For one exact live reviewer generation it may:

1. ingest an already stable typed input, callback, or receipt without a model
   call;
2. classify a genuinely idle callback boundary from content-free evidence;
3. reserve the existing shared one-nudge ceiling before one fixed submit-only
   recovery prompt;
4. re-read identities and deadline immediately before delivery;
5. publish the accepted resource-free callback and continue the owned stage;
6. close only exact-owned superseded reviewer resources.

Unknown ownership, an active or permission prompt, a stale generation, a dead
provider, malformed/oversized/symlink artifacts, an exhausted ceiling, or an
insufficient deadline produces typed attention with zero speculative effect.
A process loss after the durable submit reservation is deliberately ambiguous:
the next worker reports `callback-submit-effect-uncertain` and never replays
the paste or Enter. Deterministic kill-point tests cover crashes immediately
after each external transport effect.
The coordinator wake path applies the same rule independently of model
transport: it serializes one exact operation, persists write-ahead phases before
paste and Enter, and treats any partially observed delivery as
`callback-wake-effect-uncertain`. Concurrent reconciliation and crash replay
therefore cannot emit a second provider-facing wake.
Accepted and duplicate callback receipts are subject to the same generation,
operation, run, callback and payload identity checks before they can suppress
recovery. A continuation writes a `paste-reserved` receipt before the external
paste; after that boundary replay may prove the changed editor or fail closed,
but it never pastes the prompt again.
Every Enter delivery is likewise preceded by a durable `submit-reserved` or
`submit-retry-reserved` receipt. If the process stops between reservation and
the external key effect, replay never guesses that the key was absent: it
observes exact current-generation activity or records typed attention with zero
second Enter.
After a submit-recovery generation reaches exact broker acceptance, the harness
finalizes that exact operation/run/lane/generation/target binding against the
durable callback receipt, idempotently under concurrent workers, while
preserving its consumed nudge/restart budgets. A later generation in the same
retained reviewer session is therefore observed normally while active, but it
cannot gain a second recovery prompt or Enter.
If the worker crashes after durable `state=sent` but before the separate
submit receipt reaches `sent`, restart reconciles only that exact receipt from
the authoritative sent state before classification. It never repeats the
provider prompt or Enter, preserves the consumed budgets, and turns a malformed
receipt into typed attention instead of silently accepting the mixed phase.

Codex's exact native rate-limit model-switch dialog is also harness-owned for
unattended work. When the default first option is visibly selected, the harness
chooses `Keep current model` once, preserving the route-bound model and leaving
future reminders enabled. Any changed or unknown choice still receives zero
input and fails closed.

Same-session verification also separates a successful cmux RPC from semantic
submission. A continuation receipt is acknowledged only after the exact
retained provider enters a recognized activity state or produces an exact
accepted callback receipt. Prompt text may remain visible in terminal history;
an idle repaint, permission prompt, unknown screen, failed child, raw input
file, target swap, or ownership change never counts as acknowledgement. If the
editor remains exactly input-ready, the harness may send Enter once more
without repasting, only after consuming the same liveness reservation. An
unconfirmed result is `continuation-submit-unconfirmed`, never a false success.
If the exact screen disappears after the first Enter, delivery stops at that
typed unconfirmed result immediately; the retry budget cannot turn missing
observation into a second Enter.
Activity visible before the current prompt is confirmed in the input editor is
treated as stale. Once a durable submit receipt exists, activity may acknowledge
the continuation, but a still-visible editor becomes attention and never causes
another Enter.
Before a new prompt transport, the harness snapshots the exact visible editor.
The current paste is acknowledged only after that editor state changes; a stale
editor containing the same reusable heading is not sufficient. Provider
activity after Enter must likewise differ from the input-ready baseline.
Codex's native `Pasted Content … chars` editor form is treated as input-ready,
not as an idle prompt, and the gate and runtime persist the same
generation-bound continuation effect identity. A coordinator-owned recovery
that has already restored exact lane ownership also restores the prior
`awaiting-resolution` phase before rebuilding the moved-HEAD context packet.

## Harness-owned control plane

The release includes an executable authority matrix for plan steps, loops,
review, verification, bounded fix/retry, checkpoint, callback and cleanup.
Lifecycle transitions are chosen by code-owned policy from validated typed
artifacts; terminal model prose cannot select or repeat a lifecycle effect.
Manual `current` and `resume` remain recovery/diagnostic ingress, not the normal
unattended path.

The deterministic missing-submit incident runs against the exact v2.6.3
snapshot and the fixed candidate. It proves the original callback timeout,
bounded recovery, callback acceptance, next-stage progression, shared budget,
zero duplicate prompt/provider effect, complete resource-free parent/child
cleanup, and an actual `reap-ready` next pipeline boundary without long
wall-clock sleeps. Its
identity-bound receipt is
`docs/acceptance/v2.6.4-unattended-missing-submit-dogfood.json`.
The release receipt no longer treats direct test calls as unattended effects.
One effect-recorded scenario enters through the production review-gate facade,
accepts the callback wake, performs exact resource cleanup, and enters the
task-summary observer through `finish_task_summary` to publish `reap-ready`.
The older direct-helper scenario remains unit coverage only and is excluded
from release evidence.
The final executable authority trace is retained separately in
`docs/acceptance/v2.6.4-harness-control-plane-final.json`; it binds every
approved lifecycle stage to harness ownership and records zero manual/model

Callback recovery also distinguishes a stale accepted receipt from the current
generation after reservation. If current typed input/callback evidence wins
that race, the reserved effect is settled without a prompt or Enter. Liveness

The final release audit also closed three late boundaries: an accepted callback

## Durable coordinator decisions

Escalations, resolutions and amendments are append-only, hash-linked records.
`.task-needs-attention.json` contains a bounded authoritative pointer rather
than the full mutable decision. Writers persist the immutable record before
publishing the pointer; readers validate the chain. A historical full marker
is read-compatible and receives one deterministic backfill during resolution.
Repeated operations preserve identical bytes instead of erasing earlier
decisions.

## Purpose-safe plan review

`task-review-runner.py plan` is the supported plan-review command. It always
uses `purpose=intent`, validates one Outcome Contract, protects the capability
dispositions and success-evidence map, and supplies exact base/head Git object
IDs plus bounded `review-inspect` commands. Ambiguous base selection, malformed
protected regions, or legacy `current --plan` without a compatible explicit
boundary fails before a provider starts. The compiler also compares the exact
working bytes of the repository plan and every explicit protected artifact to
`git show HEAD:<path>` before materializing a provider boundary, so dirty or
uncommitted review subjects cannot inherit an unrelated HEAD identity.

A design-only correction can continue retained reviewer lanes while binding
both reviewed/resolved plan digests and the exact Git delta. Changing Outcome,
dispositions, or evidence requires an append-only amendment and fresh boundary.
Review inspection continues to reject symbolic and abbreviated object IDs.

## Wiki Stop self-healing

Before a validation-blocked Stop, the canonical vault parser may plan one
transactional repair for an unresolved wikilink whose target is unique by exact
frontmatter title or H1. The shared fence/inline/alias/anchor-aware rewrite
primitive updates through `vault-write.py`, then the hook rebuilds derived
indexes and runs one full strict validation. Ambiguous, missing, malformed,
unsupported embed, or concurrently changed cases remain untouched and blocked.
The same exact planner-owned repair may update `wiki/log.md` or `wiki/hot.md`
when the broken link lives on a writer-owned surface. This is not general page
write authority: the writer recomputes the canonical repair and accepts only
identical optimistic bytes; forged or ordinary writer-owned updates fail.

## Upgrade from 2.6.3

Finish or reconcile live operations before updating. After obtaining the new
repository bytes through the user's normal approved Git workflow:

```bash
python3 scripts/upgrade-preflight.py --root .
python3 scripts/codex-adapter.py --apply
scripts/mcp-gateway/mcp-gateway.sh codex-sync --apply
python3 scripts/harness-cli.py doctor
make test-harness
```

Start a new Claude/Codex session so generated plugin metadata and skills reload.
No operation-store or PipelineSpec migration is required. Historical decision
markers remain read-compatible and are upgraded only through the normal
resolution path.

## Rollback

No migration is introduced. Roll back through the normal versioned installation
path to 2.6.3, rerun adapter/MCP sync checks, and retain append-only decision,
callback, review and release evidence. If any active operation has ambiguous
ownership across the version boundary, leave it at typed attention instead of
rewriting the store or closing resources manually.
