# LLM Obsidian v2.7.8

Version 2.7.8 is a bounded stability candidate for the two defects exposed by
the 2.7.7 release runs plus the verification-control cleanliness and
structural-pivot cleanup defects exposed while qualifying this candidate. It
does not introduce a scheduler, lifecycle or store owner, provider fallback,
retry budget, public schema, dependency, or replay path.

## One-shot protected-research cleanup

- Research prompts delivered in the provider argv retain their exact prompt
  pointer as cleanup authority. Before publishing input acceptance, the worker
  requires the current pointer bytes to equal the exact prompt bytes already
  persisted as the final research argv element. Mismatch uses the existing
  attention containment and publishes no `input-accepted` event.
- After the callback broker accepts the exact result, the runtime publishes
  the accepted payload digest as `result-published`. The ordinary process and
  resource observations then complete the existing sequence:
  `provider-started`, `input-accepted`, `result-published`, `process-exited`,
  `resource-closed`.
- The research fetch can therefore close and create its synthesis child
  without another prompt, provider send, or network fetch. Missing or
  mismatched generation, prompt, result, callback, or resource evidence stays
  fail-closed.

## Untyped escalation remains fail-closed

- The state-only `suppressed-stale-post-self-heal` classifier is removed.
  Even a complete predecessor and canonical awaiting successor cannot identify
  which step produced an untyped executor raise.
- Every untyped raise therefore uses the ordinary append, attention, notify,
  and coordinator-send path. No public escalation schema or API was added.
- `v278-suppress-stale-post-self-heal-escalation` remains deferred until a
  separate approved contract binds the incoming raise to exact operation, run,
  visit, callback, and successor identity.

## Verification-control cleanliness

- Dispatch-owned local Git exclusions now name the verification packet,
  response, and decision-contract files exactly. These files remain runtime
  transport and cannot make an authorized same-HEAD retry appear product-dirty.
- The retry still observes the complete tracked-and-untracked product tree;
  any unrelated untracked or modified product file remains visible and blocks
  verification.
- The regression creates all three real control files after dispatch setup and
  proves the scoped Git status is empty and every exclusion is installed once.

## Structural-pivot cleanup

- Runtime cleanup recognizes a structural-pivot parent only when its delegated
  child is the exact existing `review-round` kind and the child parent, lane,
  run, generation, accepted callback digest, provider, and resource evidence
  all match.
- The already accepted pivot can therefore publish `resource-closed` and clear
  ownership without replaying a provider, review, or callback.
- The repair adds no new cleanup abstraction or public contract; missing or
  mismatched identity remains fail-closed through the existing checks.

## Quality and repository boundary

The target repository base `379e772c` and this candidate both measure the
unchanged active review-authority manifest at exactly 27 files / 15,603 lines,
with zero writable authorities and zero incident literals. The earlier 15,663
diagnosis belongs only to `llm-obsidian-swarm` integration commit `71f0b27c`,
which contains a 60-line `runtime_worker_liveness.py` repair not present in the
target repository. That repair is not ported, and 15,663 is not target
headroom.

`scripts/harness/runtime_session_launch.py` is 1,155 lines under its existing
1,157-line hotspot ceiling. The exact candidate contains 290 Python files /
109,373 lines after the ambiguous suppression machinery was removed and the
structural-pivot cleanup gap was closed, 275 lines below the unchanged
109,648-line ceiling and with no ceiling expansion.
