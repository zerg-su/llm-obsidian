# LLM Obsidian v2.6.7 RC6.4

RC6.4 is a narrow autonomous-review continuation candidate over exact RC6.3
base `8f4340ff11903676377a809625e0713558e2e3c3`. It adds no scheduler, daemon,
provider retry, callback replay, or generic attention self-heal.

## Recovery boundary

- One pure classifier recognizes a terminal `changes-requested` review whose
  identity-bound resolution changed product HEAD, whose new HEAD has complete
  exact-HEAD verification, whose effects are empty, and whose next review
  iteration remains within the configured ceiling. The existing worker poll
  rearms that continuation once.
- The same classifier recognizes one immutable review callback already
  accepted by the `OperationStore` but not yet consumed by its exact review
  gate at the dispatch root's durable `review-drive-failed` boundary. The
  worker invokes the existing gate workflow once without accepting the
  callback again or relaunching its provider.
- A canonical prepared/finalized recovery receipt binds root run and revision,
  review attempt, gate digest, and verification or callback authority. A crash
  after preparation converges; finalized, conflicting, or drifted receipts do
  not retry.
- A terminal approval is bound to both the exact product HEAD and the reviewed
  implementer-summary digest. If only that summary changes after launch, the
  finalization ledger admits exactly one normal predecessor-bound follow-up;
  unchanged summaries reuse approval idempotently, while any additional packet
  drift is rejected before a callback or provider effect.
- If that follow-up terminates with no lane or provider effect, the next
  invocation admits predecessor callback scratch only after the existing
  content-addressed rollover proves one exact archived approved owner. It then
  supersedes and rearms the failed attempt within the same product cycle; an
  unbound, mismatched, live, ambiguous, or current-attempt callback is refused.

## Fail-closed behavior

Pending or uncertain effects, mismatched owner/run/lane/attempt identities,
ambiguous callbacks, malformed evidence, active unaccepted review, stale
verification, and exhausted review ceilings remain typed attention. Existing
same-generation `wiki-summary-invalid`, `callback-wake-effect-uncertain`, and
`pipeline-verification-effect-uncertain` latches retain their restart-only
semantics. An absent, root-level `callback-invalid`, or other unrelated latch
cannot authorize accepted-callback ingestion.

Diagnostics report stable receipt-bound `review-drive-recovery-*` and
`review-callback-ingestion-*` reasons. They project durable authority and do
not infer a second recovery policy.

Coordinator-owned reap resolves the current session from the task's frozen
runtime before using the generic cross-runtime helper. This narrow authorized
adapter repair prevents a stale inherited foreign-runtime variable from
rejecting the exact registered reap while preserving all origin-session and
finalization identity checks.
