# ADR: use passive callback-deadline reconciliation; do not add a callback watchdog authority

## Status and outcome

**Accepted design for RT1; no production change is made by this task.**  The
callback watchdog is the existing harness runtime worker's deterministic,
code-owned deadline check plus receipt-driven reconciliation.  It may record
typed `attention-required` on an expired callback wait, but it never sends
agent input, starts a model, restarts/cancels a provider, or closes a cmux
surface.  The existing task-screen watchdog remains a separate advisory
observer; the supervisor remains limited to exact native trust and armed-exit
dialogs.

This establishes an architectural boundary, not a scheduler or a new lifecycle
authority.

## Problem and non-goals

An operation can be durably in `awaiting-callback` while a provider result or
callback is delayed, lost, or present but not yet ingested.  The fallback must
make that condition visible and recoverable without token spending, extra
provider surfaces, or guessing ownership.

Non-goals are production implementation in RT1; a new scheduler, pipeline
engine, or model-owned watchdog; model polling or periodic model calls;
changes to review budgets, permissions, cmux public API, or lifecycle
authority.

## Facts established by inspection

- `OperationStore` atomically persists immutable operation identity, revisioned
  legal transitions, exact owned resources, and callback receipts under an
  owner lock (`scripts/harness/store.py`).
- `CallbackBroker.accept` admits one callback only for the exact operation and
  run, records its id/kind/SHA-256 receipt in the same transition, rejects
  invalid/late/different receipts, and makes a duplicate an idempotent no-op
  (`scripts/harness/callbacks.py`).
- `runtime_worker.enforce_callback_deadline` asks `OperationSupervisor` to
  turn an expired reviewer callback wait into
  `attention-required/callback-timeout`; the worker writes only a typed,
  content-free timeout marker (`scripts/harness/runtime_worker.py`).
- The worker already probes content-free liveness on its owned loop.  Its
  evidence is state/revision, process status, digests, and receipt digest;
  `LivenessController` persists owner-only state and idempotent action receipts
  (`scripts/harness/liveness.py`, `scripts/harness/runtime_worker.py`).
- Exact resource reconciliation only acts after fresh exact ownership probes;
  unknown or orphaned ownership fails closed to attention rather than cleanup
  (`scripts/harness/reconciliation.py`, `scripts/harness/cli.py`).
- The cmux adapter exposes exact surface/workspace status and exact cleanup
  primitives, while `cmux_task_watchdog.py` observes screen progress and sends
  notifications only.  It is not a callback-recovery authority.

## Alternatives considered

| Alternative | Result | Operational trade-off |
| --- | --- | --- |
| Passive deadline reconciliation at existing worker/facade drives | **Chosen** | No new process or provider effect; an idle host has no invented polling path, and an expired wait becomes durable typed attention. |
| Event-driven provider exit/progress handler | Rejected as the primary fallback | Useful evidence already feeds owned liveness/reconciliation, but exit/progress alone cannot prove that a callback was delivered or safely recover a missing receipt. |
| Bounded host heartbeat that launches a separate watchdog | Rejected | Adds scheduling, duplicate state/ownership, and a new failure/recovery surface; even a cheap heartbeat would compete with the existing worker and lifecycle facade. |

## Decision and ownership

The owner of callback recovery remains the operation's existing runtime worker
and `OperationStore` ledger.  On every ordinary worker drive it first attempts
stable callback ingestion.  If no callback was accepted and the exact
reviewer-parent deadline has elapsed, `enforce_callback_deadline` performs the
sole durable transition to `attention-required` with reason
`callback-timeout`.  Callback acceptance races this safely: the broker checks
the deadline and receipt under the store lock, so an expired review receipt is
rejected without consuming the child callback.

The ordinary lifecycle facade (`harness-cli.py` `status`, `inspect`, `resume`,
`reconcile`, `cancel`, `close`, `doctor`) remains the only operator entry
point.  `reconcile` reads exact process/surface identity before any existing
cleanup action; it does not manufacture provider work.  A caller who sees
`attention-required` can use the existing diagnose/resume path, which remains
fail-closed for unknown ownership, pending effects, malformed callback data,
or a missing continuation budget.

No observer is allowed to write a receipt, alter an operation state, inject a
message, terminate a process, or close a surface.  In particular, the cmux
screen watchdog may show a warning/alert/recovery notification only; it must
not be connected to callback ingestion or reconciliation.  The supervisor's
native-dialog automation remains restricted to the exact trust and armed-exit
prompts it already recognizes.

## Control and data flow

```text
provider writes typed callback/result
        |
runtime worker stable-reads exact callback pointer
        |-- valid exact receipt --> CallbackBroker + OperationStore --> finalizing/verifying
        |-- absent receipt -----> deadline not reached --> continue existing drive
        `-- absent receipt -----> deadline reached --> attention-required(callback-timeout)
                                                              |
                                                   harness-cli diagnose/resume/reconcile
                                                              |
                                             fresh exact liveness + ownership evidence
                                                              `--> existing legal transition only
```

Provider liveness and progress are evidence, not authority: the worker's
content-free liveness state can observe a process exit, stable typed result, or
accepted receipt.  A receipt suppresses liveness recovery; a stable result is
reconciled through the existing callback-specific path.  Cleanup is permitted
only by the existing exact-owner reconciler after an accepted receipt or a
fresh resource probe.  Deadline expiry itself never implies provider death,
permission, cleanup, or a model call.

## Failure recovery and security boundary

Malformed, oversized, mismatched, duplicate, late, or expired callbacks remain
within the broker's typed rejection boundary.  Process/surface ambiguity,
unreadable owner-only state, or exhausted recovery budget is
`attention-required`, not automatic recovery.  Receipt bodies and screen text
must not enter watchdog/liveness state; only bounded identifiers, state,
numeric timing, and SHA-256 digests may be persisted or emitted.

The selected design has zero new network, permission, model, or cmux-control
effects.  It preserves the current provider/runtime sandbox and does not grant
a background pane authority to answer a prompt.  Any future proposal that
adds a timer outside the runtime worker, a provider wake/restart, an input
send, or cleanup must be treated as a new architecture decision and reviewed
for lifecycle, permissions, and public-interface impact.

## Rollout, rollback, and stop criterion

Rollout is documentation-first: retain the current deadline/receipt behavior,
exercise its hermetic seams, and observe content-free `callback-timeout` and
liveness telemetry during the RT dogfood window.  There is no feature flag or
runtime migration for RT1.  A later implementation is allowed only after this
decision remains compatible with dispatch, review, reap, and protected research
flows and passes the acceptance seams below.

Rollback of a future change is removal of that change back to this passive
deadline design; do not replace it with a parallel heartbeat.  Stop and raise
an architecture-level failure if the same callback wait repeatedly reaches
attention with (a) a valid exact receipt already durable, (b) ambiguous
ownership, or (c) any proposed recovery requiring provider input/effect.  The
next action is read-only diagnosis and coordinator classification, not another
automatic retry loop.

## Deterministic test seams and acceptance

| Seam | Deterministic assertion |
| --- | --- |
| Callback broker | Exact run/operation only; duplicate receipt is idempotent; a deadline race leaves the parent in `callback-timeout` and does not consume the child receipt (`tests/harness/test_callbacks.py`). |
| Runtime deadline | Expired live reviewer waits produce only typed attention/marker; a handled callback suppresses that transition (`scripts/harness/runtime_worker.py`). |
| Liveness | Evidence and action receipts contain hashes, states, and counters but no screen/callback body; receipt evidence produces `observe`, not a model effect (`scripts/harness/liveness.py`). |
| Reconciliation | Dead process/alive exact surface closes only that surface; orphaned/unknown ownership does not mutate (`tests/harness/test_callbacks.py`, `scripts/harness/reconciliation.py`). |
| cmux observer | Warning/alert/recovery notifications are staged, content-free state excludes screen text, and no sampling result becomes lifecycle authority (`tests/test_task_lifecycle.py`). |
| Diagnostics | A pending durable review callback is emitted as a bounded, content-free, `model_required: false` signal (`tests/harness/test_diagnostics.py`). |
