# LLM Obsidian 2.6 dogfood RT4 callback fallback prototype

Date: 2026-08-02

Disposition: **partially-achieved**

## Question

Can the existing `OperationStore`, process/supervisor identity, callback
receipt/outbox, and cmux surface signals provide a code-owned fallback that
distinguishes live progress, provider exit without a callback, and a durable
callback awaiting ingestion without a model call or a repeated provider effect?

## Reproducible evidence

Run this single deterministic local fixture from the repository root:

```bash
python3 tests/harness/test_liveness.py
```

It passed on this task branch.  The fixture creates only temporary directories;
it starts no provider, invokes no model, and has no network or cmux side effect.

| Required state | Existing durable/runtime signal | Observed fallback result | Evidence status |
| --- | --- | --- | --- |
| live-progress | Changed cmux screen digest with an alive, non-interactive process and unchanged operation record | `observe`, with the idle clock reset and `model_call=False` | Established as one live-progress observation; insufficient for the complete `rt4-signal` outcome |
| exited-no-callback | `process_status="dead"` for the identity-bound provider process, with no callback or receipt digest | Classified separately from live idle, but selects `restart` and marks `model_call=True` | Classification established; safe no-effect fallback missing |
| durable-callback-pending-ingestion | Current callback target plus matching accepted callback receipt; receipt generation and operation ID must match the current target | The receipt digest is treated as current liveness progress (`observe`); a prior generation is rejected as non-progress | Receipt validation established, but no distinct pending-ingestion classification or resume/reconcile result exists |
| typed result without callback | Two stable bounded result reads, with no callback or receipt digest | `reconcile-result`, with `model_call=False` | Established (`rt4-durable-result`) |

The controller stores content-free state and idempotent recovery receipts in
owner-only files.  A replay of the same observation does not create a second
receipt.  This is the only prototype artifact; production modules and tests
remain unchanged.

## Decision

The existing signals are sufficient to observe live progress and to reconcile a
stable typed result without a callback.  They also distinguish provider death
from live idleness and validate that a receipt belongs to the current callback
generation.  They are **not** sufficient for the proposed no-model,
no-repeated-effect fallback on provider exit: the code-owned decision for a
dead process is the existing bounded `restart`, which is explicitly
model-effectful.

Accordingly this disposable spike does not establish the desired end-to-end
fallback and must not be promoted into production from this result.

Outcome-evidence disposition: `rt4-signal` is **missing** because its required
third state lacks a distinct pending-ingestion classification; `rt4-no-model-poll`
is **contradicted** because provider death selects `restart` with
`model_call=True`; `rt4-portability` is **established only as an explicit
unproved-runtime limitation**; and `rt4-durable-result` is **established** by
this durable report.

## Portability and limitations

The signal contracts are repository-shared: `docs/runtime-capabilities.md`
lists `OperationStore` harness operations and operation telemetry for both
Claude Code and Codex CLI.  This run exercised only the deterministic local
fixture, not an actual provider/supervisor/cmux surface on either runtime.
Consequently it cannot prove that process identity, screen digest availability,
or receipt-to-ingestion timing are portable in live Claude and Codex sessions.

Residual gaps:

1. Define and prove a non-model, non-retrying disposition for
   `exited-no-callback` (for example, durable attention or exact external
   reconciliation) before claiming the requested safe fallback.
2. Exercise the exact three states on live Codex and Claude/cmux task surfaces
   and retain runtime-specific evidence for process identity, surface signal,
   callback outbox, receipt, and ingestion timing.
3. If a pending accepted receipt needs a different action from ordinary
   `observe`, add an explicit outcome contract and production change in a
   separately approved task; this prototype deliberately adds neither.
