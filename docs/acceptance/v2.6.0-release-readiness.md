## Cheap harness coverage boundary

The 2.6 release adds a hermetic transition matrix and a repeatable coverage
ratchet. The matrix exhausts every supported operation-state source/target
pair, every built-in pipeline observation combination, simple/deep mixed
review dispositions, and every Wiki Summary outcome/evidence/gap shape. It
contains 4,370 enumerated combinations; additional effect lifecycle, callback
routing, and malformed persisted-contract cases fail closed outside that
count.

`make test-harness-coverage` runs the fake/unit harness suite without models or
network and combines stdlib `trace` counts with an AST statement denominator.
The canonical manifest includes internal harness modules plus dispatch, review,
reap, outcome, resolution, telemetry, task and summary entrypoints. It observes
all 76 declared modules and reports 10,179 / 13,842 statement lines (73.54%
weighted). Critical direct-process ratchets include contracts 98.9%, state
machine 97.4%, callbacks
90.4%, store 94.9%, liveness 86.9%, pipelines 84.5%, review gate 85.9%, runtime
sessions 74.1%, and runtime worker 78.3%.

This is deliberately not presented as global 100% line or branch coverage:
stdlib `trace` does not merge child-process execution, while cmux/provider/OS
boundaries remain integration evidence. The release's 100% claim is limited to
the explicitly enumerated supported transition combinations. The code-owned
coverage gate prevents the weighted and critical-module floors from regressing;
the manifest explicitly excludes only the provider-launch `review-runner.py`
and provider/OS `live-acceptance-runner.py`, each owned by its separate live gate.
Future work can raise the ratchets or adopt a subprocess-aware coverage tool
without weakening this boundary.

## Final purpose-bound review contract

The final review program binds additive receipts to exact evidence instead of
using one overloaded review as every gate. Intent review checks the Outcome
Contract and approved plan; implementation review checks exact product HEAD and
verification evidence; release review checks the exact integration HEAD,
outcome-evidence map, accepted deviations, and merge drift. Small reversible
work may collapse intent, but this release-risk change requires all three.

The deep implementation/release checks have two independent lanes:

- Fable/spec must classify the approved plan, every Outcome Contract evidence
  item, the RT3 partial boundary above, scope/non-goals, and release readiness;
- Sol/standards-correctness-architecture-security must inspect the cumulative
  release implementation and its highest-risk paths, not just this ledger.
