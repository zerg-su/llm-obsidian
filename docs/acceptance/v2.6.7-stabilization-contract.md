# 2.6.7 stabilization denominator contract

Subject: release 2.6.7 from base tag `v2.6.6-rc4-fix3`
(`5ac90ef94029371507320d900f32c4c0b254d790`).

The authority for the stabilization denominator is the versioned config
`config/v267-stabilization-subject.json` plus the read-only validator
`scripts/v267_stabilization.py`. This page is an operator map only; it grants
no runtime transition authority and duplicates no rule. When this page and the
config disagree, the config wins.

## What the lifecycle subject digest binds

`lifecycle_subject_sha256` hashes the sorted `(path, blob)` pairs of every
tracked path at HEAD that the versioned subject rules classify as behavioral:
production Harness/dispatch/review code (`scripts/`), behavioral runtime
config (`config/`), schemas, hooks, behavior-changing skills, agent
definitions, runtime plugin wiring, and the behavioral documents
(`AGENTS.md`, `CLAUDE.md`, `docs/runtime-capabilities.md`,
`docs/task-sessions.md`, `docs/skill-references/`).

Excluded, so they never reset the RC1 live streak: `wiki/`, ordinary `docs/`
(including this page and `docs/acceptance/evidence/`), `references/`,
`tests/`, `evals/`, `examples/`, `prototypes/`, `_templates/`, user Obsidian
state (`.obsidian/`, `.raw/`, `.vault-meta/`, `.claude-memory/`), CI
(`.github/`), MCP profile examples, root-level markdown other than
`AGENTS.md`/`CLAUDE.md`, `LICENSE`, and `Makefile`.

Paths the rules do not recognize classify as behavioral. The digest fails
closed while any behavioral tracked path is dirty or a behavioral path is
untracked.

## Operator commands

```bash
# Current lifecycle subject digest (clean behavioral tree required)
python3 scripts/v267_stabilization.py digest

# Explain how specific paths classify
python3 scripts/v267_stabilization.py classify wiki/log.md scripts/harness/cli.py

# RC1 streak verdict from gate-bound run receipts (exit 0 = complete).
# Receipts must bind the configured cells in config/acceptance-cells.toml
# ([rc1], --manifest) and artifact evidence resolves against --root.
python3 scripts/v267_stabilization.py streak \
  --receipts docs/acceptance/evidence/v2.6.7/rc1-streak-receipts.json \
  --expected-digest <lifecycle_subject_sha256> \
  --manifest config/acceptance-cells.toml \
  --root .

# Release stop rule over the typed defect ledger (exit 2 = stop)
python3 scripts/v267_stabilization.py ledger \
  --ledger docs/acceptance/evidence/v2.6.7/rc1-defect-ledger.json
```

## RC1 gate workflow (production preflight facade)

`scripts/live_acceptance_rc1_gate.py` is the production consumer of the three
configured `[rc1]` cells. It sequences the streak, contains unauthorized
runs, and emits/records the authoritative schema-2 receipts; every receipt
decision is delegated to the `v267_stabilization` streak authority. Live
cells remain coordinator-authorized one at a time and launch only through
the existing dispatch owner (`scripts/dispatch-runner.py`).

```bash
# Declaration + next cell (read-only; exit 0, exit 3 on a broken declaration)
python3 scripts/live_acceptance_rc1_gate.py preflight --json

# Reserve exactly the next configured cell and launch its engineering/change
# corridor through the coordinator-approved dispatch spec. Restart-safe: a
# crashed run resumes the same reserved cell. Refuses without explicit
# coordinator authorization, before any state or launch effect.
python3 scripts/live_acceptance_rc1_gate.py run \
  --coordinator-authorized \
  --expected-digest <lifecycle_subject_sha256> \
  --dispatch-spec <coordinator-approved-spec.json> \
  --approval-token <token>

# Complete the reserved cell with its authoritative receipt. Only a
# reservation whose corridor actually launched may be recorded, and the
# receipt must carry the launched dispatch request identity. The whole
# receipt list re-validates through the streak authority before anything
# is persisted; a fabricated or tampered receipt leaves the durable state
# untouched.
python3 scripts/live_acceptance_rc1_gate.py record \
  --expected-digest <lifecycle_subject_sha256> \
  --receipt <run-receipt.json>
```

## Receipt and ledger shapes

Run receipts use `schema_version` 2 and bind the configured gate exactly:
`cell_id`, `sequence`, and `corridor` must equal the configured cell;
`executor_route`/`review_route` must equal its registered routes;
`provider_session_ids` must exactly match the accepted executor/reviewer run
identities re-derived from the durable runtime records; and
`material_cycle` is either `null` or the five durable artifacts, where each
file artifact is `{path, sha256}` contained under the configured evidence
root with matching content bytes, and each file parses as a typed JSON
evidence record binding its own kind, the run's exact `cell_id`, and the
corrected HEAD (`head_sha`; the re-review must carry `verdict: approve`). A
receipt is only a selector: positive authority is re-derived from the exact
dispatch-run identity, the request-owned `OperationStore`, accepted executor
and reviewer callbacks, successful verification effects, the trusted review
gate, the bound `FinalizationLedger`, successful reap, and terminal
`OwnedResources()`. `fix_head` must equal the exact approved worktree HEAD.
Arbitrary well-hashed bytes, caller success/resource claims, and legacy
schema-1 receipts fail closed.
