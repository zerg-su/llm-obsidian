# LLM Obsidian 2.6.3: documentation quality contracts

These contracts are release evidence, not an installed skill. The evaluated
`document-project` candidate was removed under the approved no-improvement stop
condition. Existing planning, TDD, review, and repository contracts remain the
execution path.

## Source hierarchy and claim ledger

Prefer executable schema, public CLI behavior, compiled configuration, and
tests; then repository operating contracts and release metadata; then maintained
versioned product documentation; then protected pinned primary sources. Treat
secondary explanation as interpretation.

For each material claim record:

| Claim | Audience/job | Authority | Version | Verification | Disposition |
|---|---|---|---|---|---|
| What the reader may do | Exact job | File, command, or source | Applicability | Cheapest honest check | Established, deferred, or rejected |

A generated synthesis is never authoritative. A citation proves source
identity, not that the local interpretation or implementation is correct.
Resolve contradictions in favor of the project contract and record the ruling.

## Audience and job coverage

Define each audience by entry knowledge, desired result, permissions, and
failure cost. Coverage uses an audience/job denominator:

| Audience | Entry knowledge | Job | Observable result | Required forms | Evidence |
|---|---|---|---|---|---|
| New user | Clean checkout | First durable result | Validated saved artifact | Tutorial and minimal reference | Walkthrough |
| Operator | Installed project | Diagnose and recover | Safe supported state | How-to and troubleshooting | Failure drill |
| Extension author | Core mental model | Add bounded extension | Compiled and tested change | Tutorial and reference | Gate result |
| Maintainer | Repository contract | Release candidate | Exact reviewed HEAD | How-to and release reference | Release ledger |

Every row needs a navigable route and evidence. File counts, word counts,
headings, and green linters are not coverage evidence by themselves.

## Information architecture and concept order

Assign each page one primary form:

- A tutorial is learning-oriented, linear, and reaches a safe first success.
- A how-to solves one concrete job for a reader who knows the basics.
- Reference is the complete, precise inventory for its declared surface.
- Explanation builds the mental model, reasons, relationships, and trade-offs.

Organize by user need, not source-tree layout or authoring chronology. Build a
concept dependency graph before ordering pages. Introduce each prerequisite
before dependent action; keep translations stable. A link does not replace a
definition required to finish the current step.

## Shared page contract

Every instructional page states its reader, assumed knowledge, observable
result, version applicability, prerequisites, optional components,
permission/effect boundary, and authoritative sources.

A tutorial begins from a reproducible state, follows one complete path, shows
expected observations, ends with independent verification and supported
cleanup, and links the next useful form. A how-to gives exact actions, expected
result, verification, likely failure, and recovery. A reference covers names,
inputs, defaults, allowed values, outputs, status semantics, permissions, side
effects, compatibility boundaries, and a minimal valid example. An explanation
defines concepts in dependency order and labels non-runnable fragments.

## Runnable-example contract

Every runnable-looking block has all seven fields:

| Field | Requirement |
|---|---|
| Prerequisites | Files, cwd, tool/runtime, optional services, permissions |
| Input | Complete command or data with no hidden substitutions |
| Expected result | Stable observable output or state |
| Verification | Independent command or artifact inspection |
| Failure | Likely actionable error and read-only diagnosis |
| Recovery | Supported retry, rollback, cleanup, or stop boundary |
| Authority | CLI help, schema, test, or source owning the behavior |

Use `json` and `toml` fences only for complete data. Use `text`, `jsonc`, or an
explicit fragment label for comments and omissions. Name destructive,
privileged, network, publish, deploy, and release effects before the command;
documentation does not grant authority to perform them.

Recovery starts from the visible symptom, continues with read-only observation
and an ownership decision, then uses the supported repair or escalation path
and independently verifies restored state. Never prescribe direct edits to
derived state or repeated external effects.

## AI and external-source controls

Classify each external practice as adopt, adapt, reject, or defer. For
AI-assisted documentation, pass the audience, job, page form, source set, and
requested operation; keep source bytes and provenance separate from generated
prose; verify citations and version-sensitive claims; use independent review;
and fail closed on unsupported claims.

Markdown accessibility checks cover descriptive headings and link text, text
alternatives for non-text content, meaningful reading order, and no meaning
conveyed by color alone. Static Markdown checks do not establish full rendered
WCAG conformance.

## Verification and completion

Run checks cheap-first:

1. Required files, headings, inventory, and placeholder checks.
2. Relative links and structured JSON/TOML/schema validation.
3. Compilation or execution of examples at the public seam.
4. Focused tests for documented behavior.
5. Fresh-context reader walkthroughs and failure drills.
6. Independent intent and engineering review.
7. Exact-HEAD release gate when release is in scope.

Completion maps evidence to the unchanged Outcome Contract. Record missing or
contradicted rows and residual gaps instead of redefining success around the
artifacts that happen to exist.
