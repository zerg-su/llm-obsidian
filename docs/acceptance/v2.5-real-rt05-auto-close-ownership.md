# RT05 auto-close ownership diagnosis

Date: 2026-08-01

## Outcome

RT05 found no current auto-close leak to repair. The observed
`auto_close_expected=1,left_open=1` event is a pre-v2.3 telemetry false
positive: a provider process returned while its task remained resumable, and
the retired lifecycle emitter inferred close expectation from static task
policy rather than terminal operation ownership. The same task session later
continued, completed, and closed its exact surface.

Current v3 dispatch ownership is correct and now has an explicit regression:
an `awaiting-callback` parent retains its exact surface, rejects terminal
cleanup, and closes no surface. No runtime close path was added or changed.

## Evidence chain

The content-free event log for session
`019f6ddd-d07e-7a30-b018-f6358753fb91` records:

1. a degraded task `left_open` event and successful provider return at
   `2026-07-18T01:03:29Z`;
2. later escalation resolution, review, reap, and task completion in the same
   session;
3. a successful exact task-surface close at `2026-07-18T01:51:38Z`.

At the legacy boundary, `cmux_agent_supervisor.py` ran `after-exit` after every
provider return. Without an armed close sentinel,
`cmux_surface_lifecycle.py` correctly did not close the surface, but labeled
the event from `interaction_policy=unattended` and
`surface_policy.auto_close=true` alone. It had no authoritative operation id,
operation state, or surface owner. `pipeline-stats.py` later counted the static
flag as a miss.

The event predates commit `04cb7ed` (`feat: port harness-first 2.3 runtime`,
2026-07-30). The runtime migration contract makes
`cmux_agent_supervisor.py` non-production and assigns provider/surface effects
to `RuntimeSessionManager` and the runtime worker.

## Current exact ownership

A v3 task has one surface-owning parent dispatch operation. Typed model-step
children share that persistent provider session and own no surface themselves.
Terminal reap:

1. requests exit for the exact recorded provider process group;
2. waits for the provider and its exact supervisor to exit;
3. refuses unknown ownership;
4. closes only the surface in the parent operation's `OwnedResources`;
5. clears those resources before marking the operation complete.

The regression in `tests/harness/test_runtime_sessions.py` invokes cleanup
while the parent is still `awaiting-callback` and proves the operation record
and exact surface remain unchanged while the close ledger stays empty.

## Boundaries with RT01 and RT02

- RT01 repaired upgrade-preflight classification for exact terminal,
  effect-settled, resource-free legacy mirrors. It did not add a close path.
- RT02 repaired abnormal-unwind release for surfaces opened by
  `live_acceptance_driver`. The RT05 event came from the retired task-agent
  supervisor and does not exercise RT02's release obligation.
- Current reconciliation already maps an exact `dead process + live owned
  surface` observation to exact close and leaves unknown ownership in
  attention.

## Decision

Do not:

- close any historical or unrelated surface;
- add a second cleanup path;
- repair the retired emitter as if it were current production;
- pair legacy records by session, because one coordinator session can own
  concurrent tasks;
- reinterpret or hand-edit the event log.

The useful RT05 product result is this bounded diagnosis plus the current
ownership regression. The original observation does not justify a runtime
repair.

## Exact replacement recommendation

Dispatch one separate observability task, distinct from RT02 and RT07:

> Emit operation-scoped, content-free surface lifecycle outcomes from the
> current `RuntimeSessionManager.cleanup` boundary after authoritative cleanup
> decisions. Bind each outcome to the exact owner and operation. Update the
> report to derive current v3 close success/miss metrics only from those exact
> outcomes. Add controls proving an `awaiting-callback` parent is neither
> closed nor counted as a miss and that an unrelated surface is never targeted.

This replacement is observability-only unless it independently reproduces a
current cleanup failure. It must not duplicate RT07's read-only stale-resource
diagnostic or change RT02's driver-scoped release guard.
