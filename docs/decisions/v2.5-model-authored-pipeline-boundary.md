# ADR: compile model-authored pipelines as bounded data

Status: accepted  
Date: 2026-07-31  
Applies to: LLM Obsidian 2.5

## Context

The 2.4 harness proved code-owned lifecycle, engineering change, and bounded
fix pipelines over one `OperationStore`, FSM, supervisor, provider runtime,
verification gate, review gate, and reap boundary. Some approved tasks still
need a different sequence of those existing operations. Hard-coding every
sequence creates presets faster than it creates reusable semantics; allowing a
model to emit Python, shell, permissions, or a mutable workflow DSL would move
the trust boundary into untrusted output.

Unattended execution also had a second reliability gap: a live executor could
write the required typed result but omit callback submission, leaving the
coordinator paused even though deterministic evidence already existed.

## Decision

The model may propose exactly one versioned `PipelineSpec` only after the
deterministic selector proves a semantic gap against the closest built-in. The
spec is strict JSON data. It may reference only registered primitives,
`executor-default`, approved context hashes, registered verification checks,
typed transitions, and explicitly bounded backward edges. It cannot contain
commands, source code, arbitrary paths, providers, credentials, dependencies,
or new capabilities.

Compilation is pure and precedes every effect. The compiler:

- rejects unknown fields, primitives, schemas, skills, transitions, routes,
  capabilities, verification checks, and duplicate pointer identities;
- requires a linear successful path ending in the existing review/reap
  boundary and permits no `parallel`/`join`;
- applies conservative node/model-call, traversal, time, token, attempt,
  permission, effect, and context ceilings;
- exposes only permission/effect classes with an enforceable code or sandbox
  binding; policy-only claims are unavailable to custom specs;
- canonicalizes set-like fields and binds the schema, primitive versions,
  compiler output, and approval card into one definition hash.

The preview renders the code-selected baseline delta, route/capability proof,
enforcement bindings, unavoidable inherited cmux authority and origin identity,
absolute worst case, loop stops, and terminal outcomes. Validation persists
only an owner-readable challenge bound to those exact inputs. A separate
coordinator/user decision produces a random one-shot approval token; launch
atomically consumes it and freezes the definition. There are no worktree,
provider, Git, cmux, network, review, or publish effects before approval.

Execution reuses the 2.4 runtime. Each custom model visit is a resource-less
child operation in the parent lane with an immutable input/output receipt.
Accepted receipts deterministically reconstruct the next transition and are
never replayed. Verification, review, escalation, cleanup, and reap remain the
existing code-owned operations. Raw specs live in owner-only runtime scratch;
content-free telemetry receives hashes, categories, and numeric counters only.

The generic liveness observer uses code-only evidence at a 60-second cadence.
A stable typed result without an outbox is submitted through the exact existing
submit port without a model call. Ten minutes of no progress is observation
only; after 15 minutes one bounded nudge is allowed; after 20 minutes one
operation-global identity-bound provider restart may consume the frozen restart
budget and resumes without replaying the original task prompt. The first missing
receipt resumes. Exhaustion creates durable typed attention.
Interactive or unknown prompts are never interrupted by the idle ladder.

## Consequences

- Custom composition adds no second scheduler, store, FSM, supervisor, CLI, or
  operation identity.
- The model decides task semantics but cannot author executable mechanics or
  widen authority.
- A repeated custom fingerprint can be reported as a promotion candidate, but
  promotion still requires a manual registry/TDD/review release change.
- `features.custom_pipeline_authoring=false` blocks new authoring while
  built-ins and already frozen runs remain replayable.
- Active operations must finish or be parked before upgrading the checkout;
  frozen definitions are not migrated in place.
- Parallel graphs, recursive graphs, user-editable runtime YAML/wiki control,
  external pipeline marketplaces, and self-authored primitives remain out of
  scope.
