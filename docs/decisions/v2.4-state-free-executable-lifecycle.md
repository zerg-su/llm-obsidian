# ADR: execute lifecycle composition through the existing harness

Status: accepted  
Date: 2026-07-31  
Applies to: LLM Obsidian 2.4

## Context

The first 2.4 implementation wrapped harness 2.3 in a second controller,
operation identity, and receipt ledger. Its strict net-value gate failed at
1,364 added non-test lines versus 100–400 honestly deletable lines, so that
design was removed and the release was temporarily narrowed to a read-only
catalog.

The user subsequently restored the full executable 2.4 goal and explicitly
authorized reconsidering the boundary. The replacement slice was required to
reuse the proven harness identity and lifecycle rather than recreate them.

## Decision

`OperationSpec.operation_id` remains the sole production identity mechanism and
the existing runtime worker remains the sole pipeline controller. A compiled
built-in definition contributes only:

- immutable semantic step order and schema validation;
- a stable semantic definition digest bound into the dispatch identity;
- state-free reconciliation of existing operation and review-gate evidence.

The reconciler neither persists progress nor launches providers. The runtime
worker performs effects through existing facades and records only a local,
idempotent review-drive receipt. The receipt binds the evidence observed before
each drive, so callbacks arriving during the facade call remain pending for the
next drive. A pending receipt plus a live gate is replayable after a crash.
Material findings are written to the task worktree as a bounded typed
`.task-review.json` packet and delivered once to the exact executor surface.
The executor commits applied/rejected resolutions or escalates; a changed HEAD
then drives same-session verification. Reap remains coordinator-owned.

The `engineering/change` verification primitive compiles into a deterministic
derived `OperationSpec`, lane, and run for its exact definition, input, profile,
and HEAD. The child uses the existing store, state machine, supervisor, and
immutable budget envelope; it does not introduce another identity mechanism or
controller. Its typed receipt links the child identity back to the dispatch
operation, and the state-free reconciler observes only that exact receipt.

A failed child may authorize one code-owned `fix-and-resubmit` iteration. The
executor must commit a different HEAD and write a typed response bound to the
failed child identity and packet digest. The worker durably accepts that
response before deriving a new verify operation. Missing, stale, mismatched, or
exhausted responses cannot replay verification or advance review.

Executor permissions use the existing exact Git-common-directory and cmux-socket
validators. The approval surface discloses the permission classes and whether
they are sandbox- or code-policy-enforced. The semantic definition digest is
not presented as a digest of host paths; route, review, verification, and
adapter bindings retain their own existing identities and validation.

## Net-value decision

The lifecycle slice measured 279 added and 40 deleted non-test lines before
review fixes. It does not satisfy the old raw-LOC inequality. That inequality
was a stop rule for the rejected second-engine design, not a permanent ban on
the user-approved functional goal. This decision explicitly supersedes it for
the state-free design because the slice:

- adds no controller, store, FSM, CLI, supervisor, or identity mechanism;
- removes model-owned review orchestration from the task contract;
- reuses the existing callback broker, review gate, runtime worker, and exact
  capability helpers;
- is guarded by hermetic asynchronous-callback and linked-worktree permission
  regressions before dogfood.

Engineering profiles must continue to reuse this seam. If they require a second
durable progress truth or duplicate provider lifecycle code, implementation
stops and returns to design.

## Consequences

- The catalog is now executable only through existing harness operations.
- Review callbacks and resolution HEAD changes advance the same gate
  idempotently; unchanged review state creates no repeated provider effect.
- The pre-approval envelope exposes exact model/review limits, side-effect
  classes, permission deltas, enforcement classes, and typed return categories.
- Existing operations started on an older checkout must finish or be cancelled
  before upgrade.
- Custom/model-authored pipeline construction remains a separate 2.5 decision.
